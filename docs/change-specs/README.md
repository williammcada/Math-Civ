# Change specifications

This directory stores **version-specific approved change contracts** for this project.

## Naming

Use the target release number, for example:

- `v0.9.2.md`
- `v1.0.md`
- `v1.1.3.md`

For a pre-versioned project, use a descriptive draft name only until a version is assigned.

## Workflow

1. Discuss and test ideas in chat.
2. Consolidate accepted decisions into a change specification.
3. Mark it **Approved** only after the target is frozen.
4. Implement against the exact canonical source baseline named in the file.
5. Preserve an implementation checkpoint.
6. Verify.
7. Preserve the verified checkpoint.
8. Package and deploy from that checkpoint.
9. Record the result in the project brief.

Historical chats are useful working context, but they are not the canonical specification once an approved change file exists.
